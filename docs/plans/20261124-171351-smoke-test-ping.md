# Draft Plan: 20261124-171351-smoke-test-ping

> **Human Review Required:** Merging this Pull Request to the default branch marks this exact file and commit SHA as approved for implementation.

### 1. Clarifying Questions and Assumptions
* **Clarifying Questions:**
  * Is Spring Security enabled, and should `/api/ping` be publicly accessible without authentication?
  * Does the application configure a global servlet context path or API prefix (e.g., via application properties) that would affect `/api/ping`?
  * Should `"task-manager"` be a fixed literal or pulled from configuration with `"task-manager"` as the value?
* **Assumptions:**
  * The project uses Spring Boot Web (Spring MVC) with Jackson for JSON serialization and JUnit 5 with MockMvc for testing.
  * The endpoint does not require database access, service-layer logic, or changes to security rules unless existing security blocks `/api/**` by default.
  * No existing `/api/ping` route conflicts with this requirement.

### 2. Scope and Non-Goals
* **Scope:**
  * One read-only `GET /api/ping` REST endpoint returning HTTP 200 and the JSON payload `{"status":"ok","service":"task-manager"}`.
  * One isolated MockMvc unit test verifying the HTTP status, content type, and JSON response body.
* **Non-Goals:**
  * Modifying existing JPA entities, repositories, or database/migration configurations.
  * Implementing deep health
 checks (e.g., database or external dependency connectivity) or adding Spring Boot Actuator.
  * Adding authentication/authorization rules or additional endpoints.

### 3. Testable Acceptance Criteria
* A `GET` request to `/api/ping` returns HTTP status `200 OK`.
* The response `Content-Type` header is `application/json`.
* The response body strictly contains `{"status":"ok","service":"task-manager"}`.
* Existing entities, repositories, and database configurations remain untouched.
* The new MockMvc unit test passes without requiring a live database connection.

### 4. Proposed Implementation Steps
1. **Define Response Model:** Create a lightweight, immutable response object (or map/record) containing `status` and `service` fields.
2. **Add REST Controller:** Create a dedicated REST controller mapped to `/api/ping` with a `GET` handler returning HTTP 200 and `{"status":"ok","service":"task-manager"}`. Ensure it has no dependencies on services, entities, or repositories.
3. **Add MockMvc Unit Test:** Create a web-slice test class using MockMvc targeting only the new controller, verifying status `200`, JSON media type, and exact `status` and `service` field values.
4. **Verify Build and Tests:** Run the unit test suite via the build tool to confirm the new test passes and no existing tests regress.

### 5. Test Cases, Risks, and Rollback Approach
* **Test Cases:**
  * *Primary (MockMvc unit test):* Perform `GET /api/ping` -> assert HTTP 200, `application/json` content type, `status` equals `"ok"`, and `service` equals `"task-manager"`.
* **Risks:**
  * **Security Blocking:** If Spring Security is active, `/api/ping` may return `401`/`403` unless permitted in security configuration, and the MockMvc slice test may need security filters bypassed or configured.
  * **Web-Slice Context Issues:** Global configuration annotations on the main application class (such as JPA auditing) can sometimes cause web-slice tests to fail if entity/database beans are excluded.
  * **Route Prefixing:** A pre-existing server context path could alter the runtime URL.
* **Rollback Approach:**
  * Revert the commit or delete the newly added controller, response model (if separate), and MockMvc test file. Because no entities, schemas, or database configurations are modified, no data or migration rollback is required.
