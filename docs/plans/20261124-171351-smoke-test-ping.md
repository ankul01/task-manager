# Draft Plan: 20261124-171351-smoke-test-ping

> **Human Review Required:** Merging this Pull Request to the default branch marks this exact file and commit SHA as approved for implementation.

### 1. Clarified Decisions and Assumptions
* **Confirmed Decisions (from Review Feedback):**
  * **Security:** Spring Security is not enabled; no authentication or security filter configuration changes are needed for `/api/ping`.
  * **Routing:** No global servlet context path or API prefix is configured, so the endpoint will be served directly at `/api/ping`.
  * **Service Name Configuration:** The `"task-manager"` value for the `service` field will be pulled from application configuration (configured with `"task-manager"` as its value) rather than hardcoded as a literal in the controller.
* **Assumptions:**
  * The project uses Spring Boot Web (Spring MVC) with Jackson for JSON serialization and JUnit 5 with MockMvc for testing.
  * The endpoint does not require database access or service-layer logic.
  * No existing `/api/ping` route conflicts with this requirement.

### 2. Scope and Non-Goals
* **Scope:**
  * One read-only `GET /api/ping` REST endpoint returning HTTP 200 and the JSON payload `{"status":"ok","service":"task-manager"}`, with `service` populated from application configuration.
  * Configuration of the service name property with `"task-manager"` (if not already present in non-database application properties).
  * One isolated MockMvc unit test verifying the HTTP status, content type, and JSON response body.
* **Non-Goals:**
  * Modifying existing JPA entities, repositories, or database/migration configurations.
  * Implementing deep health checks (e.g., database or external dependency connectivity) or adding Spring Boot Actuator.
  * Adding Spring Security, authentication/authorization rules, or additional endpoints.

### 3. Testable Acceptance Criteria
* A `GET` request to `/api/ping` returns HTTP status `200 OK`.
* The response `Content-Type` header is `application/json`.
* The response body strictly contains `{"status":"ok","service":"task-manager"}`, with the `service` field resolved from application configuration.
* Existing entities, repositories, and database configurations remain untouched.
* The new MockMvc unit test passes without requiring a live database connection.

### 4. Proposed Implementation Steps
1. **Define Response Model:** Create a lightweight, immutable response object (or record/map) containing `status` and `service` fields.
2. **Configure Service Name Property:** Ensure the application configuration defines the service name property with the value `"task-manager"` (reusing the standard application name property or a dedicated non-database property, without modifying any database settings).
3. **Add REST Controller:** Create a dedicated REST controller mapped to `/api/ping` with a `GET` handler that injects the configured service name property and returns HTTP 200 with `status` set to `"ok"` and `service` set to the configured value (`"task-manager"`). Ensure it has no dependencies on services, entities, or repositories.
4. **Add MockMvc Unit Test:** Create a web-slice test class using MockMvc targeting only the new controller, supplying/loading the configured service name property (`"task-manager"`) and verifying status `200`, JSON media type, and exact `status` and `service` field values.
5. **Verify Build and Tests:** Run the unit test suite via the build tool to confirm the new test passes and no existing tests regress.

### 5. Test Cases, Risks, and Rollback Approach
* **Test Cases:**
  * *Primary (MockMvc unit test):* Perform `GET /api/ping` -> assert HTTP 200, `application/json` content type, `status` equals `"ok"`, and `service` equals `"task-manager"` as loaded from configuration.
* **Risks:**
  * **Missing Property in Test Slice:** If the MockMvc test slice does not load the application properties file or explicitly supply the configured property, startup or property injection could fail or resolve unexpectedly. Setting the test property explicitly (or referencing the configured default) mitigates this.
  * **Web-Slice Context Issues:** Global configuration annotations on the main application class (such as JPA auditing) can sometimes cause web-slice tests to fail if entity/database beans are excluded.
* **Rollback Approach:**
  * Revert the commit or delete the newly added controller, response model (if separate), property addition (if any), and MockMvc test file. Because no entities, schemas, or database configurations are modified, no data or migration rollback is required.
